# 架构与设计文档维护规范

## 目标与 owner

修改核心模块的人同步维护对应文档；评审者核对代码、测试和文档是否一致。
这是项目协作约定，不是 CLI 自动加载的策略，也不是替代测试的安全机制。
入口固定为 [docs/README.md](README.md)，根 README 和 [AGENTS.md](../AGENTS.md) 指向此处。

每个稳定核心模块在 `docs/modules/<module>/` 下维护：

- `architecture.md`：结构、责任与为什么。
- `design.md`：实际合同、怎么执行和怎么验证。

不要为每个 helper 单建模块；依据独立职责、资源生命周期、跨模块消费者和未来维护价值拆分。
系统总览只保留组合关系，模块细节由链接定位，不在多处复制同一错误矩阵或限制表。

## 单一职责与唯一维护位置

每篇面向读者的文档必须解决一个主要任务，当前分工以[总索引的任务表](README.md#按使用任务选择文档)为准。
新增内容时先找现有 owner，不因为入口不同而再写一套相同流程。

- 根 README 是项目介绍和少量入口；总索引是完整导航，不承担操作教学。
- 101 的终点是首次成功运行；不要再塞入六阶段课程、源码逐段解读、完整回归或编程练习。
- 学习路线维护一份课程目录与方法，`tutorial/` 维护实验正文。目录落地页只导航，不再复制课程表。
- 用户参考按能力分工，完整的安装流程、参数用法、控制命令和回归清单只在各自 owner 维护。
- 模块设计维护精确合同与实现证据，用户参考只解释使用所需的含义并链接合同，不复制整份不变量或错误矩阵。
- 历史计划与验证记录保留当时事实，不改写成最新操作指南，也不因测试新增而回填旧运行的结果。

**去重不是让文档无法独立完成任务。** 101 的最小启动命令、教程为观察原理而使用的实验命令、
操作前必需的安全提醒可以出现于对应上下文；重复的是必要示例，不是第二份完整流程或参数表。
教程可保留定向测试及其学习目标，全套回归执行顺序仍链接测试参考。
如果两篇都能独立完成同一套课程或同一项环境配置，就应把流程合并到唯一 owner。

迁移内容后同时检查旧入口和源码打印的路径：
[learning.rs](../src/learning.rs) 引用 `docs/harness-learning.md`，
[lab.rs](../src/lab.rs) 引用 `docs/local-llm.md`。保留这些入口；
被已有文档引用的锚点可留下简短迁移链接，不保留第二份过时正文。

## 内容最低要求

| 架构文档 | 设计文档 |
|---|---|
| 源码入口、职责、非职责、真实消费者 | public/internal 接口和关键数据模型 |
| 上下游依赖与输入/输出方向 | 正常、取消、失败的执行顺序 |
| 状态/资源由谁创建、持有、结束 | 可验证的不变量及其实际 enforcement owner |
| 关键取舍与不选某方案的理由 | 输入校验、错误码、边界值、兼容性 |
| 变更影响范围与当前架构限制 | 测试映射、证据缺口、修改检查清单 |

无状态模块明确“没有资源生命周期”，不要虚构 manager 或状态机。
不要把“测试应该覆盖”写成“已有测试覆盖”；列出真实测试符号，并把缺失用例单独标注。
需要举例时使用合成输入；消息示例须符合当前 serde 形状，API key/真实业务内容禁止入库。

## 现状、约定和提案

- **当前实现**：能够定位到当前源码、配置或测试的行为，用现在时写。
- **维护约定**：团队希望维持的合同，明确由编译器、运行时检查、测试或人工评审中的哪一层保障。
- **未来方案**：尚未实现的设计，单列为未实现或链接[迁移路线](helixent-migration.md)。

发现文档和实现不一致时，不以文档为理由暗中改变代码。先说明差异；在获授权的实现范围内修代码，
或按现状修文档并保留真实限制。架构说明不能覆盖更具体的设计合同，任何合同又不能自证已经落地。

## 修改触发器

| 变更 | 必须核对的文档 |
|---|---|
| 模块新增、拆分、合并或职责迁移 | 总索引、系统架构、相关模块的文档对 |
| API、消息/事件字段、工具 schema、错误/退出码 | owner 设计文档及直接消费者 |
| 所有权、spawn/join、取消、队列、超时、资源释放 | 架构生命周期及设计的状态/失败路径 |
| 权限、路径限制、进程隔离、凭据处理 | 对应设计、安全限制和用户 README |
| 文档职责调整、教程拆分或操作步骤迁移 | 总索引、所有入链、源码打印的路径；新旧 owner 不得同时保留完整流程 |
| 仅局部实现整理，以上语义均不变 | 可不改文档；评审说明 no semantic change |
| 一次运行测试或任务进度 | 不写入稳定模块文档，不机械新增 changelog |

重大跨模块取舍需要在相应架构文档说明依据；若需要保留被替代方案的历史，再单独引入 ADR。
目前不预建空的 ADR 目录，也不把所有 commit 都当成架构决策。

## 可重复的维护流程

1. 从总索引定位 owner，阅读模块的两份文档和直接消费者。
2. 阅读源码及相关测试，列出 missing/stale/accurate 的关键 claim。
3. 更新真正承载合同的最少文件；地图变化才改索引，用户行为变化才改使用说明。
4. 检查相对链接、锚点和代码/测试符号；确认源码与文档没有相反的承诺，也没有两个同职责流程。
5. 对涉及的接口、取消、权限与限制逐项核对，必要时补回归测试，而不是靠注释保证正确性。
6. 提交或评审时说明改动语义、文档和测试；发布仍需要独立授权与门禁。

文件引用使用仓库内相对链接，加上符号名定位；避免依赖随格式化漂移的硬编码行号。
稳定模块文档不重复维护运行次数、测试总数或临时 artifact hash；这些放在阶段验证记录中。
篇幅接近 400 行时按子职责拆分；不要复制一整份源码或把未来 roadmap 混入现行接口表。

## 验证边界

纯文档变更以链接与锚点、模块覆盖、证据追溯、职责边界和 diff 检查为主，可运行已有回归辅助核对。
带命令的改动还应检查 shell 语法和实际参数入口，区分“命令可解析”与“真实服务已经跑通”。
运行时变化则按风险执行 [CI](../.github/workflows/ci.yml) 及真实协议/副作用测试。
当前 CI 没有文档内容一致性或模块双文档覆盖自动检查；这两项仍由维护者与评审执行。
