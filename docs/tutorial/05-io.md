# 第 5 课：宿主生命周期——谁读输入，谁写输出，谁负责退出

[学习路线](../harness-learning.md) · 上一课：[控制执行](04-control.md) · 下一课：[回归验证](06-regression.md)

## 本课要解决的问题

模型回答完成后，为什么程序有时还不能退出？用户不再输入、输出端不读数据时，谁来停止谁？
本课把调试器放回 CLI 宿主，理解 Rust 所有权如何约束输入、运行、输出的关闭顺序。
完成后，你应该能指出 Sender、Receiver、stdin fd、Agent 和取消 token 的 owner，而不笼统归因于“异步”。

建议预留 45–60 分钟；前置是[环境准备](00-setup.md)和第 4 课。
以下命令在仓库根目录执行；Step 2 的 Lab 对照需要本地 Ollama，已有确定性测试不需要模型。

## Step 1：从一个完全不需要模型的输出开始

```sh
cargo run --quiet --locked -- learn io
echo $?
```

应显示课程并退出 `0`。在 [main.rs](../../src/main.rs) 找到 `Command::Learn` 分支，按次序阅读：

1. 建立容量为 1 的 channel。
2. 把课程字符串作为 `OutputItem::Notice` 移入 Sender。
3. 显式 `drop(sender)`，关闭发送端。
4. `output::forward(receiver, ...)` 输出内容，队列排空后结束。

这里没有 Agent、模型或 stdin 控制读取。Rust 的“移入”意味着 receiver 的消费责任交给 forward；
Sender 被释放后，receiver 在读完已有内容时得到 `None`。不是课程输出完一个字符串就猜测“不会再有数据”。
现在预测：如果还保留一份 Sender，forward 的下一次 `recv().await` 会不会知道生产者已经结束？
把预测写进笔记，Step 3 会在真实运行里找到答案。

## Step 2：用 `/dev/null` 区分自动模式与交互模式

先确认本地服务与锁定基线正常。依次运行，**每条运行后马上读退出码**：

```sh
bash scripts/harness-lab.sh --case chat --auto --lesson io </dev/null
echo $?
```

成功条件是 `[PASS]` 且退出 `0`；模型不遵守场景或基线不可用时可能失败，应保留实际错误。
自动模式虽然显示暂停摘要，但 sink 已根据真实暂停事件提交 Step；屏幕显示摘要的时刻不保证 Agent 仍在等待。
它不创建 `DebugInput`，所以没有 stdin 也能运行；这里不是“把 EOF 当成继续”。

然后运行交互模式：

```sh
bash scripts/harness-lab.sh --case chat --lesson io </dev/null
echo $?
```

在预检成功、输出健康时，应看到 `[CANCELLED]` 并退出 `130`，不会推进模型动作。
`/dev/null` 被输入模块识别为立即 EOF；control 把 EOF 转成取消，而不是永久等下一条命令。
如果退出 `1`，检查预检、输入或输出错误；本实验的 `130` 结论不是所有 EOF 与完成竞速的通用定律。

再运行不访问模型的自动化证据，每条应命中一个测试：

```sh
cargo test --locked --test lab_cli lab_auto_chat_ignores_stdin_and_inherited_cloud_configuration -- --exact --nocapture
cargo test --locked --test lab_cli lab_eof_and_quit_cancel_without_running_a_model -- --exact --nocapture
```

后者通过真实子进程的控制管道验证 EOF/q；它不依赖你手动按键，也不等同于 `/dev/null` 类型分支的穷尽测试。
若报告 `0 tests`，先核对名称，不能把空运行计入学习证据。

## Step 3：找到三个 future 的汇合点

打开 [main.rs](../../src/main.rs) 的 `execute`，按以下顺序找代码，不必从参数定义逐行读起：

1. `let mut agent`：模型、Registry、配置移入 Agent，历史只有这个 owner。
2. `let run = async`：调用 `agent.run_debug(...).await`，运行期间持有 Agent 的独占借用。
3. `let writer = async`：取得唯一 Receiver，调用 `output::forward`；出错则发取消信号。
4. `let control = async move`：持有 `control_sender`，借用 controller/input，并选择等待命令或结束信号。
5. `tokio::join!(run, writer, control)`：三个 future 在同一个执行组合中并发推进，必须都结束。

`async` 先构造 future，不会自动开线程；这里也没有给三者分别 `spawn` 后遗忘 JoinHandle。
因此宿主仍掌握它们的借用与完成边界，而不是靠进程退出清理后台任务。
工具内部可能有自己的 worker，不能把“宿主没有 detached task”推广成“整个项目没有 worker”。

现在沿正常完成路径画箭头：

```text
Agent 返回 → run_done 通知停止输入 → control 返回并释放 control_sender
          → Lab oracle / 最终 Notice → run 释放 sender
                                   → writer 排空，recv 得到 None → join 返回
```

箭头表示依赖，不保证两个发送者的结束先后；最终要求是它们都被释放。
如果只释放 run 的 Sender，control 仍在等待一条永远不会来的输入，writer 也看不到 EOF，join 就可能等不完。
`run_done` 专门解决这个关闭环，不是重新取消已经完成的 Agent。

亲手验证开放 stdin 也能正常结束：

```sh
cargo test --locked --test lab_cli lab_default_read_shortcuts_pause_inspect_and_finish_with_stdin_open -- --exact --nocapture
```

应运行一个测试；阅读 [tests/lab_cli.rs](../../tests/lab_cli.rs) 中这个测试和 `Interactive::finish`，
找出测试没有先关闭输入再等退出的证据。不要把普通 shell 进程结束后 stdin 自动关闭当作同一证明。

## Step 4：理解慢输出为何会反向取消运行

先读 [main.rs](../../src/main.rs) 的 `enqueue`，再读 [output.rs](../../src/output.rs) 的
`forward`、`Output::stdout`、`Output::write_all`，回答每一层在等谁：

1. Agent 的同步事件回调不能 `await` 慢终端，因此只做 `try_send`。
2. channel 当前限制 64 个 OutputItem，不是 64 KiB；大快照仍可占较多内存。
3. 队列满/关闭时，宿主记录首个错误并取消 run；它不是可靠消息队列，也不会无限重试。
4. writer 对可 poll 的 stdout 使用非阻塞 fd；部分写入后只推进尚未写出的 slice，不重发前半段。
5. writer 出错仍先通知取消；宿主继续等待运行收尾，不能直接 drop 正在执行工具的 future。

在 `forward` 中找 2 秒写入预算和取消后的 100ms 尝试：二者作用于当前输出项，
不是整个运行或整个队列的绝对退出期限；序列化也不在这个写入 timer 内。
普通文件走同步写入，异常文件系统阻塞不能用 Tokio timeout 强制中断。

不要自行拼一个无限输出或永久堵塞的脚本；运行已有真实管道故障测试：

```sh
cargo test --locked --test cli_http blocked_stdout_does_not_block_ctrl_c_or_process_exit -- --exact --nocapture
```

应命中一个测试。打开 [tests/cli_http.rs](../../tests/cli_http.rs) 对应函数，确认它在发 SIGINT 和等待退出期间
**保持 stdout 不读**，进程退出后才取回输出；提前排空会掩盖这个回归。
测试要求非零退出和 `stdout stalled`，不是要求终态必达或退出必为 `130`。
输出可以停在 NDJSON 半行；下游必须同时检查进程状态、EOF 和完整记录。

## Step 5：把取消与 fd 释放连起来

回到 `execute` 最后的 `select!`：Ctrl-C 分支先设置 token，再 `execution.await`。
最后检查 writer、队列、输入和 Agent 错误；所以屏幕出现 Completed 不自动保证进程成功退出。

阅读 [debug_input.rs](../../src/debug_input.rs) 与 [output.rs](../../src/output.rs) 的 `Descriptor::drop`。
两者都持有复制出来的 owned File；Drop 负责关闭自己的 fd，并尝试恢复原 flags。
`dup` 得到新 fd 数字，但共享 open-file description；stdin/stdout 同属一个终端时会互相影响非阻塞 flags。
这就是 input 要先创建、晚于 writer 释放的原因，不是可以随意交换的局部变量整理。
恢复失败和 SIGKILL 不保证执行完整清理；RAII 不能承诺强杀后的事务恢复。

## 自检与学习记录

写下三个问题的答案：auto 为什么无需 stdin？为什么 run 完成还要通知 control？
看到 `[PASS]` 之后进程非零退出，应信哪一个？

<details>
<summary>参考答案</summary>

auto 的 sink 在实际暂停事件上发送 Step，不创建输入读取器。交互 control 持有另一份输出 Sender，
需要 run_done 停止等待输入并释放它，writer 才能排空至 EOF。PASS 是一次 oracle 的内容通知，
不是整个宿主交付成功；必须检查进程退出码，输出错误仍可让成功场景非零退出。

</details>
